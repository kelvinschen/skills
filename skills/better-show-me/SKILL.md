# Better Show Me

把技术事实组织成清晰易读、便于定位和继续探索的呈现界面。内容紧扣主题；通过清晰分层、直观关联和按需展开来降低理解成本。 **以用户使用的语言呈现**。

先明确读者要回答的问题与观察范围，再提取足以支撑判断的关键事实。用户指定媒介时遵从指定；短解释直接用文本，空间关系复杂或需要独立浏览、分享时使用 HTML。

## 解释性表达

- 面向具备通用技术背景、初次接触实现的读者：过程题讲清主体、条件和结果；结构题讲清包含、依赖或所有权；决策题讲清比较维度与选择条件。代码符号与证据跟随对应关系。
- 标题明确主题与章节重点，导语直接给出核心结论；正文用完整句子讲清因果与边界。
- 上下文交代：补充理解所需的背景与范围，确保脱离原对话分享时也能独立看懂。
- 术语首次出现交代角色，后文统一命名；图表节点保持精炼，文字补充图中尚未表达的条件与原因。
- 用具体主体和动作解释事实，判断强度与证据一致。“完整闭环”“底层物理诱因”等抽象评价不能代替具体说明。已经交代的结论不在多个章节换词复述。

## 输出构造

这些是组织内容的决策，不是输出目录；章节名称来自主题本身。

- 开头用简短导语回答问题，并只补充理解该回答必需的上下文。完整规则与背景沿正文就近展开。
- 选择一个能承载完整主要关系的视图。过程可以是起点 → 跃迁 → 结果；静态结构保留关系方向和所有者，不补造执行顺序。
- 增加辅助视图前，明确它回答了主视图无法回答的哪个问题。同一过程换成时序、卡片和因果链，并不自动产生三个独立视角；可把所需差异并入主视图。
- 原因、条件、状态和证据跟随对应节点或判断。关键结论紧邻真实的代码符号、路径或局部切片；有助于验证时才提供精准链接。
- 已知事实、依据事实的推断和未知项保持可辨。示意内容明确其范围；缺少证据时保留未知，不为图表补齐未经证实的节点、状态或保证。
- 用户需要完整代码时，作为独立附件交付。

## 任务方向

| 方向 | 核心诉求 | 常用组合 |
| --- | --- | --- |
| 理解现状 | 它由什么组成，如何工作 | 组件树、浅文件树、调用树、轻量时序、数据转换链、状态路径 |
| 理解变化 | 什么变了，会影响哪里 | 语义 Diff、行为前后、影响范围、局部代码 |
| 定位排查 | 预期与实际从哪里分叉 | 预期/实际分叉、故障因果链、状态快照、路径追踪 |
| 做出决策 | 方案差异与取舍是什么 | 对齐比较、权衡矩阵、方案骨架比较 |

仓库级请求以高层地图为入口，再围绕分析主题渐进展开。模块或逻辑级请求直接聚焦关键机制与证据。

## 原语与媒介

选择原语前先阅读 [references/primitive-system.md](references/primitive-system.md) 的关系选型入口，再读匹配原语的定义与示例；示例约束关系语义，不要求复用案例内容或页面篇幅。选定媒介后，再读取一份渲染指南：

- 文本输出：[references/rendering-text.md](references/rendering-text.md)
- HTML 输出：[references/rendering-html.md](references/rendering-html.md)，在关系结构确定后组合模板原语

## 质量标准

- 主视图在首屏或首段形成闭环，细节随后按需展开。
- 脱离原会话独立分享时，读者仅凭上下文与导语也能快速读懂。
- 逻辑关系比罗列清单更醒目，关键结论比视觉装饰更醒目。
- HTML 视觉主次分明且留白充分；降低阅读负担是指减少同一视区的焦点冲突，而非省略必要信息。
- 名称、状态与结论均有真实代码或数据支撑。
- 每个辅助视图必须提供一个独立的分析视角，否则并回主视图。
- 交付前沿用户问题检查正文与视图：关系是否完整、事实是否一致、是否重复解释了同一判断。HTML 按渲染指南结合已有工具能力检查。
